# 为什么「17 · 桶自洁」清掉后又出现 —— 二次排查报告

- 时间：2026-10-31 22:55
- 版本：`versionCode 71 / versionName 0.15.2`（已在手机上）
- 现象：22:50 我装完新版时看到「暂无使用洗衣机」，但你在 22:52 再看，17 号的桶自洁计时**又回来了**
- 结论：**去重的“记忆”依附在计时器记录上，而计时器到点会被 `prune()` 删掉，记忆随之丢失 → 下一轮轮询重新建一条**
  （第一版修复方向对，但去重键存错了地方）

---

## 1. 现象时间线

| 时间 | 观察 |
|---|---|
| 22:50 | 装 0.15.2 后重启 App，「我的洗衣机」= 暂无使用洗衣机（重复记录被 `dedupeByOrder` 清掉，恰好在两条记录之间） |
| 22:52 | 你再看，17 号那行又出现了（倒计时重新开始） |

也就是说：**不是没修掉，是“删掉 → 又建”的循环**。

---

## 2. 根因（代码级）

### 2.1 去重判据挂在“活的计时器”上

`PangguaiMine.kt`

```kotlin
if (WashTimerStore.hasOrder(context, o.orderNo)) return@forEach   // 只查当前列表
WashTimerStore.start(..., startAt = now, orderNo = o.orderNo)
```

`WashPlanTimes.kt`

```kotlin
fun hasOrder(context: Context, orderNo: String): Boolean =
    orderNo.isNotBlank() && read(context).any { it.orderNo == orderNo }   // 读的是计时器列表

fun prune(context: Context, now: Long = System.currentTimeMillis()) {
    val alive = read(context).filter { it.endAt() > now }   // ← 到点就删
    if (alive.size != read(context).size) write(context, alive)
}
```

### 2.2 循环怎么形成的

1. 官方 `order/list` 里 17 那笔 0 元单**仍是 status=2**（机器卡在 code=2，订单没关闭）
2. 每轮轮询 → `autoStartTimers()` 看到它 → `hasOrder()` 查列表 → **上一轮那条已经被 prune 删掉了** → 返回 false
3. 于是又 `start(startAt = now)`，新建一条满格 5:00 的计时器
4. 5 分钟到点 → `prune()` 删除 → 回到第 2 步

**这就是“怎么清都还在”的机制**：真正的记忆应该跟订单走，不该跟计时器走。

### 2.3 为什么 `reconcileTimers()` 没兜住

```kotlin
busy && System.currentTimeMillis() >= w.endAt() && !w.abnormal -> markAbnormal(...)
```

新建的计时器 `endAt` 在未来 5 分钟，所以**永远不满足 `now >= endAt`**，异常分支永远进不去；
等它到点，又被 prune 删了，于是又从头开始。

### 2.4 为什么 22:50 那一眼是空的

22:50 重启时 `prune()` 刚删掉旧记录、新一轮还没到（轮询间隔 15–60 秒），恰好落在空窗里。你 22:52 再看，已经重建完了。

---

## 3. 影响面

- 只影响「订单在官方侧卡住不关闭」的情况（17 号现在就是）
- 正常洗完的单：官方 status 变 3 → 不再出现在 `order/list` → 不会重建，表现正常
- 副作用：每 5 分钟写一次 SharedPreferences、每轮多一次 `hasOrder` 扫描，可忽略

---

## 4. 修复方案（待你确认后动手）

核心一句话：**把“这个订单处理过没有”存成独立、长期保留的记录，不再依赖计时器是否还活着。**

1. 新增持久化集合 `handled_orders`（SharedPreferences）：
   `orderNo → state(started / done / abnormal) + 时间戳`，保留 24 小时后清理
2. `hasOrder()` 改为查 `handled_orders`，不再查计时器列表
3. `prune()` 只负责删计时器显示记录，**不动 `handled_orders`**
4. `reconcileTimers()` 里 `markAbnormal` 成功后，把 `handled_orders[orderNo] = abnormal`，该订单永不再建
5. 机器恢复空闲时，把状态改为 `done`（仍保留 24 小时，避免同订单复活）
6. 迁移：启动时把现存计时器的 orderNo 全部补写进 `handled_orders`

（方案不改你定的两条约束：不做“连续 2 分钟判异常”，仍然只在“到点后”用官方 `remainTime/code` 做权威复核。）

---

## 5. 一句话总结

不是重复记录没清干净，而是 **去重记忆存在了会被 `prune()` 删除的计时器里**：
官方订单卡在 status=2 → 计时器到点被删 → 下一轮重新建 → 无限循环。
修法是把记忆搬到独立的 `handled_orders`，与计时器生命周期解耦。
