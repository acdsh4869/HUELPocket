# 17 号「桶自洁」为何一直不结束 —— 排查报告

- 时间：2026-10-31 22:35
- 现象：App「我的洗衣机」里 `17 · 桶自洁` 一直在倒计时，反复回到 5 分钟，机器也一直显示「使用中」
- 结论：**两个独立问题叠加**——机器侧卡在占用态 + 我们本地计时器被反复重建

## 2. 机器侧：卡在「占用态」，并没有真的在洗

官方接口 `goods/normal/details`（17 号，`goodsId=1100472264`）现在稳定返回：

```
name            = 17
remainTime      = 0            ← 没有剩余时间
deviceErrorCode = 2
deviceErrorMsg  = 设备工作中，请更换设备使用
soldState       = 2
```

判断：
- `remainTime=0` 说明**没有在跑的任务**；
- `code=2 / 设备工作中` 说明机器仍被标记为「被占用」；
- 两者矛盾 → 典型的**订单未正常关闭**：机器跑完（或从未真正开始）后，服务端没有把设备状态回落。

诱因大概率是那笔 **0 元桶自洁订单**：0 元单在官方流程里是否会自动完结，我们此前没有验证过；从现象看，它把设备锁在「工作中」了。

> 这一条我们在客户端修不了，只能：①在胖乖里把这笔订单结束/取消；②或等机器侧心跳超时自动回落。

## 3. 我们 App 侧：计时器被反复重建（这是我的 bug）

### 3.1 代码位置

`app/src/main/java/com/huelpocket/app/ui/life/PangguaiMine.kt` → `autoStartTimers()`

```kotlin
val already = existing.any {
    it.machineName == o.machineName &&
        kotlin.math.abs(it.startAt - o.payTimeMillis) < 5 * 60_000L   // ← 去重条件
}
if (already) return@forEach
WashTimerStore.start(..., startAt = now)   // ← 但写入的是 now
```

### 3.2 问题

今天为了修「倒计时按订单创建时间算，导致显示已结束」，我把 `startAt` 从 `o.payTimeMillis` 改成了 `now`，
**但没有同步改去重条件**——去重仍在比较 `startAt` 和 `payTimeMillis`：

- 订单 `payTimeMillis` = 21:43（下单时间）
- 本地计时器 `startAt` = 22:28（首次观测时间）
- 两者相差 45 分钟 → `already` 永远为 false → **每次进入页面/重启 App 都会再建一条新计时器**，`startAt` 又被刷新成“现在”，倒计时回到 5:00。

22:28（04:32）→ 22:31（05:00）就是 App 重启后重建造成的。

### 3.3 加重问题

`autoStartTimers()` 只看「订单 status=2」，**不看机器是否真的在跑**。所以即使机器已经跑完、只剩一个僵死订单，我们照样起计时器，用户看到的就是“永远在洗”。

## 4. 结论

| 现象 | 归因 |
|---|---|
| 机器一直「使用中」 | 官方侧订单未关闭，设备状态卡在 `code=2`（0 元单嫌疑最大） |
| App 倒计时一直不结束 | 本地计时器去重失效，重启/刷新即重建，倒计时反复回到 5:00 |
| 两者叠加 | 看起来像“17 号一直在洗” |

**不是机器真的在洗 30 分钟**，是状态卡住 + 我们显示错误。

---

## 5. 修复建议（待你确认后动手）

1. **去重改成按订单号**：SharedPreferences 存 `timer_order_<orderNo>`，同一订单只建一次计时器（不再用 `startAt` 比对）
2. **建计时器前加机器状态校验**：`remainTime>0` 才建；`remainTime==0 && code==2` 连续出现超过 2 分钟 → 判为「设备状态异常」，不建计时器，UI 显示「设备状态异常，请到现场确认」
3. **僵死订单兜底**：本地计时器到点后如果订单仍是 status=2 且 `remainTime=0`，把该订单记为「疑似未关闭」，不再重复建计时器
4. 建议同时把「0 元单是否会自动完结」单独验一次（用 243 号机做，不影响 17）
